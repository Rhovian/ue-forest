# UE 5.8 native MCP + Niles + version control

> Status: pre-setup research. Where it conflicts with [AGENTS.md](../../AGENTS.md) or the [smoke test](../smoke-test.md) (e.g. the lead, not a worker, owns the editor), those win.

Research findings, 2026-10-04. Documentation-verified; nothing tested on a live Mac/UE 5.8 install. Repo-relative links point into the niles repo.

UE 5.8 ships native MCP as an **Experimental engine plugin**, not merely a roadmap item: Epic announced the release on June 17, 2026 and explicitly described the integrated MCP plugin. [Epic release announcement](https://forums.unrealengine.com/t/unreal-engine-5-8-released/2729274), [Epic feature announcement](https://www.unrealengine.com/news/state-of-unreal-2026-top-news-from-the-show).

**Recommendation:** start with one editor, one Claude Code or Codex worker that owns all editor operations, and Git + LFS for the project. Other Niles workers handle text/code in Git worktrees. No Niles implementation change is needed for this setup: it launches ordinary agent CLIs in the selected directory and does not manage their configuration. This is a proposed workflow, not a tested Mac integration. 1. Native MCP: verified behavior

The engine plugin is `ModelContextProtocol`, located under `Engine/Plugins/Experimental/ModelContextProtocol`; its modules are ModelContextProtocol, ModelContextProtocolEngine, and ModelContextProtocolEditor. [Epic plugin index](https://dev.epicgames.com/documentation/unreal-engine/API/PluginIndex/ModelContextProtocol).

- Enable **Unreal MCP** and **All Toolsets** in Edit → Plugins; Toolset Registry follows automatically. Restart. General → Model Context Protocol in Editor Preferences controls Auto Start (default off).
- The editor hosts the server: `http://127.0.0.1:8000/mcp`; port/path configurable. Streamable HTTP/SSE supported; stdio/WebSocket unsupported. No authentication; loopback defaults and Origin checks are not authorization.
- `ModelContextProtocol.StartServer [port]`, `StopServer`, `RefreshTools`, and `GenerateClientConfig <Client|All>` manage it. Generated JSON merges; Codex TOML refuses overwrite.
- Tools include actors, lighting, material instances, Slate inspection, automation; Python/C++ toolsets are extensible. Discovery defaults to `list_toolsets`, `describe_toolset`, `call_tool`. Shipping toolsets advertise no Resources/Prompts.
- Not strictly editor-only: commandlet startup supports `-ModelContextProtocolStartServer` / `-ModelContextProtocolPort=N`; cooked builds can host explicitly registered tools. Registry adaptation is editor-only. Headless workflow parity remains unverified.
- Calls run serially on the game thread; Epic explicitly says clients should not overlap calls.

All six bullets: [Epic Unreal MCP guide, setup/configuration/runtime/limitations](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-mcp-in-unreal-editor?application_version=5.8).

Blueprint graph editing, PIE controls, arbitrary console execution, and an unrestricted Python-execution tool in the **native shipped inventory** were not verified. Do not infer them from community bridges. Verify against the actual installation’s discovery schemas. Dedicated PCG manipulation and MetaHuman asset creation/property tools are documented separately. [Epic PCG guide](https://dev.epicgames.com/documentation/unreal-engine/working-with-pcg-and-llms-using-unreal-mcp-in-unreal-engine?lang=en-US), [MetaHuman 5.8 notes](https://dev.epicgames.com/documentation/metahuman/metahuman-5-8-release-notes-in-unreal-engine).

**Mac status:** Epic documents UE 5.8 on macOS, but I found no explicit MCP-specific Mac support matrix or Mac test result. Treat MCP-on-Mac as unverified pending a smoke test, not as unsupported. Epic’s 5.8 requirements table says Sonoma 14.5 minimum, Xcode 26.0 minimum / 26.1.1 recommended, and Xcode 26.4 incompatible. The same page has inconsistent OS wording elsewhere; use the version-specific table and verify against the installed patch. Native MCP has no documented Mac-specific caveat in the reviewed guide. [Epic Mac requirements](https://dev.epicgames.com/documentation/unreal-engine/macos-development-requirements-for-unreal-engine?lang=en-US).

3. Agent connections and configuration placement

Niles’ actual built-ins are **Codex, Claude, Hermes, pi**; Gemini is not built in. Custom executables/arguments can be defined in `niles.yaml`. [src/agents/families.rs:89](https://github.com/Rhovian/niles/blob/main/src/agents/families.rs:89), [src/config/spec.rs:24](https://github.com/Rhovian/niles/blob/main/src/config/spec.rs:24).

| CLI | Configuration for endpoint `http://127.0.0.1:8000/mcp` |
| --- | --- |
| Claude Code | Project `.mcp.json`: `{"mcpServers":{"unreal-mcp":{"type":"http","url":"http://127.0.0.1:8000/mcp"}}}`. Project servers have an interactive approval step; approve in the intended project before dispatch. [Claude docs](https://code.claude.com/docs/en/mcp) |
| Codex | Trusted project `.codex/config.toml`: `[mcp_servers.unreal-mcp]` followed by `url = "http://127.0.0.1:8000/mcp"`. Locally, `codex mcp --help` printed add/get/list/remove/login/logout and `--config` overrides. |
| Gemini CLI | Project `.gemini/settings.json`: `{"mcpServers":{"unreal-mcp":{"httpUrl":"http://127.0.0.1:8000/mcp"}}}`; `httpUrl` means streaming HTTP, while `url` selects SSE. Needs a custom Niles agent binding. [Gemini configuration](https://geminicli.com/docs/reference/configuration/), [MCP docs](https://geminicli.com/docs/tools/mcp-server/) |
| Hermes | `~/.hermes/config.yaml`, under `mcp_servers`, server entry with `url: http://127.0.0.1:8000/mcp`. No project-local config equivalence was verified; avoid putting a shared editor endpoint in every worker’s global configuration. [Hermes MCP docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp/) |
| pi | Niles’ tested 0.73.1 explicitly has no built-in MCP; use an extension or external CLI bridge. No standard project MCP config to forward was established. [pi 0.73.1 README](https://raw.githubusercontent.com/badlogic/pi-mono/v0.73.1/packages/coding-agent/README.md) |

**Inference:** Niles need not forward MCP traffic or config. Config must exist where the worker’s CLI discovers it. `--worktree` creates a sibling checkout and launches there, so untracked/generated files in the original checkout do not automatically follow. Provision only the editor owner’s configuration; if using multiple editors, each worker needs the matching endpoint. An HTTP endpoint selects an editor process, not the caller’s Git branch: changing the agent’s working directory does not retarget that editor. [src/worker/worktree.rs:71](https://github.com/Rhovian/niles/blob/main/src/worker/worktree.rs:71), [src/worker/spawn.rs:89](https://github.com/Rhovian/niles/blob/main/src/worker/spawn.rs:89), client docs above.

**Recommendation:** treat each editor as a single-writer resource for whole tasks, including human edits. Game-thread serialization does not make a multi-call editing sequence transactional. Let other agents send requests to the owner through Niles’ existing messaging; do not give every worker the endpoint. `niles --help` printed `spawn`, `send`, `wait`, `report`, `close`; `niles spawn --help` printed `--tree PATH` and `--worktree BRANCH`.

4. Version control on Mac

`.uasset` / `.umap` are binary and cannot use ordinary text merging; exclusive ownership prevents conflicting edits. UE’s default documented providers are Perforce and SVN. [Epic Perforce workflow](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-perforce-as-source-control-for-unreal-engine), [Epic source control](https://dev.epicgames.com/documentation/unreal-engine/source-control-in-unreal-engine?lang=en-US).

| Choice | Relevant tradeoff |
| --- | --- |
| **Git + LFS — recommended here** | Fits Niles’ Git worktrees directly. The Git editor provider’s historical status is beta; the maintainer’s LFS extension supports Mac/Linux/Windows and locks, but its README lists older UE versions. Exact bundled-provider status and extension compatibility in 5.8 remain unverified; CLI Git/LFS avoids depending on that UI. [Git plugin maintainer](https://github.com/SRombauts/UEGitPlugin), [Niles worktree implementation:54](https://github.com/Rhovian/niles/blob/main/src/worker/worktree.rs:54) |
| Perforce / Helix Core | Built-in UE workflow, Mac P4V client, server plus client workspaces. Configure binary assets with `+l` exclusive-open. Prefer when artist-facing checkout/locking outweighs Git worktree compatibility. `--tree` can launch Niles in an existing P4 workspace; `--worktree` remains Git-only. [Epic setup](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-perforce-as-source-control-for-unreal-engine), [P4 Mac client](https://www.perforce.com/resources/video/p4/perforce-p4-beginners-guide-version-control-basic-concepts), [exclusive-open docs](https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/P4Guide/resolve.lock.exclusive.html), [src/worker/spawn.rs:70](https://github.com/Rhovian/niles/blob/main/src/worker/spawn.rs:70) |
| Plastic / Unity VCS | Mac clients, Unreal plugin, Smart Locks retain asset ownership along a development branch until integration to the destination branch. Good binary/branch workflow; use native UVCS workspaces with `--tree`. Exact 5.8 Mac plugin compatibility unverified. [Mac release notes](https://docs.unity.com/en-us/unity-version-control/release-notes/11), [Unreal plugin](https://docs.unity.com/en-us/unity-version-control/vcs-plugins/unreal-plugin), [Smart Locks](https://docs.unity.com/en-us/unity-version-control/use-smart-locks) |
| Diversion | Mac desktop and Unreal plugin officially supported. Soft locks are advisory; hard locks prevent other users’ commits and currently require Studio/Enterprise. Separate native workspaces per agent; vendor says agent workspace cloning currently downloads the full repository. Use `--tree`, not Git worktrees. Exact UE 5.8 plugin compatibility unverified. [Mac plugin](https://docs.diversion.dev/unreal/unreal-engine-plugin), [hard locks](https://docs.diversion.dev/hard-locks), [agent workspaces](https://docs.diversion.dev/agent-quickstart) |

**LFS lock caveat:** locks are remote repository-relative paths owned by a user; the API says `ref` is for authentication rather than advanced branch-lock semantics. Therefore worktrees do not create independent lock namespaces, and several agents using one identity are not mutually excluded. Keep an explicit owner per asset/path; hold the lock through integration to the team branch, and verify the hosting service supports/enforces locks. Local edits are not a security boundary. [LFS locking API](https://github.com/git-lfs/git-lfs/blob/main/docs/api/locking.md), [lock verification config](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-config.adoc). Proposed attributes: `*.uasset filter=lfs diff=lfs merge=lfs -text lockable` and the equivalent for `*.umap`. [LFS lockable attributes](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-track.adoc).

OFPA saves actor instances in external files and is default with World Partition; it reduces level-file contention, not Blueprint/material/shared-asset contention. Include all related external actor changes when integrating; Epic warns partial submissions can leave dangling references. [Epic OFPA](https://dev.epicgames.com/documentation/en-us/unreal-engine/one-file-per-actor-in-unreal-engine).

**Multiple-editor proposal, untested:** open each worktree’s own `.uproject` in its own editor process; assign distinct ports and configs. Keep generated `Intermediate`, `Saved`, and project build outputs separate; expect disk/RAM/build overhead rather than assuming worktrees deduplicate working files. No defensible fixed GB figure was found. Git worktrees share repository metadata, not a single checkout. Reuse a DDC rather than duplicating it: UE uses local Zen DDC by default from 5.4, and shared Zen supports Mac; the Mac shared-host variable is `UE_ZenSharedDataCacheHost`. [Git worktree docs](https://git-scm.com/docs/git-worktree), [Epic DDC](https://dev.epicgames.com/documentation/unreal-engine/using-derived-data-cache-in-unreal-engine?lang=en-US), [shared Zen](https://dev.epicgames.com/documentation/unreal-engine/set-up-zen-storage-server-as-shared-ddc-for-unreal-engine?lang=en-US).

5. Minimum integration sketch and verification

Proposed first setup: designate an ordinary Niles worker as editor owner (no new compiled role); open the integration checkout in UE, configure just that worker’s Claude/Codex endpoint, and give it bounded asset tasks. Code workers use `--worktree`; merge their text changes before asking the editor owner to build/validate/save assets. Acquire asset locks before edits and release after reviewed integration. This uses existing directory selection, role briefs, messaging, and reports. [src/worker/spawn.rs:89](https://github.com/Rhovian/niles/blob/main/src/worker/spawn.rs:89), [src/workspace_manifest/types.rs:18](https://github.com/Rhovian/niles/blob/main/src/workspace_manifest/types.rs:18), `niles --help` output noted above.

Do not add an MCP endpoint manifest field yet: current manifest has role/planning/check-in bindings, not MCP orchestration. If automated per-worker editors later prove necessary, proposed minimum additions are explicit project-path/endpoint/owner binding, readiness verification, correct per-CLI config rendering, and a failure on endpoint/project mismatch. A shared-editor design would also require ownership spanning an entire task, not merely a request mutex. [src/workspace_manifest/types.rs:18](https://github.com/Rhovian/niles/blob/main/src/workspace_manifest/types.rs:18), [src/config/spec.rs:10](https://github.com/Rhovian/niles/blob/main/src/config/spec.rs:10).

Threat-model implications: Niles bypasses approvals for built-in Codex/Claude/Hermes workers and provides no isolation. An editor tool or Python bridge can mutate assets or execute code with editor-user authority; untrusted asset names/tool output can also become agent instruction input. Proposed controls: keep the endpoint local, enable only needed toolsets, make one worker responsible for saves and ownership, and review MCP configs as executable authority. Any future Niles code that manages editor execution/configuration must update `docs/security.md` to cover endpoint identity, editor-side execution and tool-output trust. [src/agents/families.rs:95](https://github.com/Rhovian/niles/blob/main/src/agents/families.rs:95), [docs/security.md:20](https://github.com/Rhovian/niles/blob/main/docs/security.md:20), [docs/security.md:88](https://github.com/Rhovian/niles/blob/main/docs/security.md:88), [AGENTS.md:72](https://github.com/Rhovian/niles/blob/main/AGENTS.md:72), [runreal execution tools](https://github.com/runreal/unreal-mcp).

Before adopting: on the actual Mac/5.8 patch, verify plugin visibility, MCP initialization/discovery, reported project identity, a read-only actor query, one reversible actor edit/save/revert, required Blueprint/PIE/Python schemas, and a two-user lock conflict against the selected host. Test two editors only if that topology is needed. These are proposed acceptance checks; none were run for this research.
